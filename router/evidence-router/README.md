# 라우터 변형 — 근거 점수 방식 (evidence scoring)

③ 라우터 파트의 **변형 하나**. 팀 합의대로 각자 다른 접근으로 만들어 브랜치별로
관리하고, 나중에 장점을 섞기 위한 초안이다.

- 브랜치: `feat/router-evidence-scoring`
- 위치: `router/evidence-router/` — 다른 변형과 폴더가 겹치지 않게 하위에 두었다.
  나중에 합칠 때 여러 변형이 한 트리에 공존할 수 있어야 비교가 쉽다.

```bash
python router.py "2025년 3분기 총 매출액은?"   # 단건 확인 (근거까지 출력)
python evaluate.py                            # 공식 30문항 + 혼동행렬
python evaluate_holdout.py                    # 평가셋 밖 24문항
python lexicon.py                             # 수집된 어휘 확인
```

의존성 없음 — 표준 라이브러리만 쓰고 DB·임베딩·LLM을 쓰지 않는다.

## 성적

| 평가 | 문항 | 결과 |
|------|:---:|------|
| 공식 `questions.json` | 30 | **30/30 (100%)** |
| 홀드아웃 (평가셋 밖) | 24 | **24/24** |
| 2차 홀드아웃 (위 둘과 겹치지 않음) | 15 | **15/15** |

참고: 기존 임베딩 유사도 프로토타입(`vector-db/pipeline/router_prototype.py`)은 30문항 76%.

**30/30을 곧이곧대로 읽으면 안 된다.** 규칙을 짜면서 그 30문항을 보고 있었으므로
조준 사격에 가깝다. 그래서 평가셋 밖 문항을 따로 두었고, 그중 1건이 틀려
`GROUPING` 규칙을 추가했다. 그 시점부터 24문항은 홀드아웃이 아니라 회귀 스위트이므로,
수정 후 값을 다시 재기 위해 2차 홀드아웃 15문항을 새로 지어 측정했다.

## 이 변형의 관점

라우터를 키워드 목록으로 짜면 평가셋에 맞춰 낱말을 적어 넣게 된다. 그래서 신호를
두 종류로 나누고, **유도할 수 있는 것은 전부 데이터에서 유도했다.**

| 종류 | 무엇 | 출처 |
|------|------|------|
| **의도 신호** | 질문이 무엇을 *원하는가* — 집계·관계·서술 | 손으로 작성 (유도 불가) |
| **근거 어휘** | 질문이 무엇에 *대한* 것인가 | `lexicon.py`가 데이터셋에서 수집 |

근거 어휘 세 가지 모두 `os_dataset/`에서 나온다.

| 어휘 | 출처 | 개수 | 가리키는 도구 |
|------|------|:---:|---------------|
| 개체 이름 | `graph/nodes.json` | 131 | `knowledge_graph` |
| 속성값 | 그래프 노드·간선 속성 (서울·금융·critical) | 47 | `nl2sql` |
| 문서 전용어 | `documents/*.md` − 위 둘 | 462 | `vector_search` |

**"문서 전용어"가 이 변형의 핵심이다.** 문서에는 Client-A도 SSL도 나오는데,
앞의 것은 그래프에도 있고 뒤의 것은 문서에만 있다. 차집합을 취하면 "문서를 봐야만
알 수 있는 낱말"이 남는다. 데이터가 바뀌면 어휘도 따라 바뀐다.

## 판별이 어려운 두 지점

세 도구가 겹치는 곳은 두 군데뿐이고, 규칙도 거기에만 필요했다.

**① "가장 많은 ~"은 집계 대상이 무엇이냐로 갈린다.**

```
"평균 연봉이 가장 높은 부서"      → 수치 컬럼을 셈  → nl2sql
"이슈가 가장 많은 제품"           → 관계를 셈      → knowledge_graph
```

같은 표현이 다른 도구를 가리킨다. 순위어 단독으로는 판별할 수 없고,
곁에 수치 어휘가 있는지 관계 어휘가 있는지를 봐야 한다.

**② 관계어가 있어도 문서 전용 기술 용어가 있으면 문서 쪽이다.**

```
"SSL 인증서 관련 장애가 있었어?"
  장애 → 관계어(REPORTED_ISSUE)      knowledge_graph +3
  SSL  → 문서에만 있는 영문 기술 용어   vector_search  +5
```

`SSL`은 그래프에도 DB에도 없다. 그래프가 답할 수 없는 낱말을 물었다면 문서 쪽이 맞다.
이 규칙은 `knowledge_graph` 도구를 직접 만들면서 "개체나 집계가 없으면 답할 수 없다"는
제약을 알게 된 데서 나왔다.

## 인터페이스 (변형 비교용 제안)

변형들을 나란히 재려면 진입점 모양이 같아야 한다. 이 형태를 제안한다.

```python
from router import route

r = route("2025년 3분기 총 매출액은?")
r.tool         # "nl2sql"
r.confidence   # 0.0~1.0 (1·2위 점수 차이 기반)
r.scores       # {"nl2sql": 8.0, "vector_search": 0.0, "knowledge_graph": 0.0}
r.reasons      # ["nl2sql +3 · 집계 표현", "nl2sql +3 · 수치 컬럼 어휘", ...]
```

`reasons`를 함께 돌려주는 이유가 있다. **나중에 변형을 섞을 때 필요한 정보는
총점이 아니라 "왜 그렇게 판단했는가"다.** 어떤 변형이 어떤 신호에 강한지 알아야
합칠 지점을 고를 수 있다. 같은 이유로 `evaluate.py`는 정확도만이 아니라
**혼동행렬**을 낸다 — 변형 A가 nl2sql↔graph 혼동에 강하고 B가 vector 판정에
강하다면 그 자체가 합칠 근거가 된다.

`confidence`는 1위와 2위의 점수 차이다. 낮으면 애매하다는 뜻이므로,
에이전트(④)가 두 도구를 모두 호출하거나 되묻는 데 쓸 수 있다.

## 알려진 약점

- **라벨 자체가 애매한 질문이 있다.** "가장 많은 프로젝트를 진행 중인 고객사"는
  평가셋 정답이 `nl2sql`이지만 `knowledge_graph`의 `HAS_PROJECT` 순위로도 답이 나온다
  (실제로 그 도구가 답한다). 지금은 수치 순위 규칙 덕에 `nl2sql`로 가지만
  근본적으로는 판정 기준이 하나가 아니다.
- **신호가 하나도 안 켜지면 `vector_search`로 떨어진다.** 문서 검색이 가장 넓게
  받아주는 도구라는 판단인데, 검증된 선택은 아니다.
- **의도 신호는 한국어 키워드 기반**이라 표에 없는 표현은 잡지 못한다.
  확장은 `router.py` 상단 표에 항목을 추가하는 것으로 끝난다.
- **`confidence` 수치는 보정되지 않았다.** 점수 차이를 6으로 나눈 값일 뿐이라,
  "0.5면 절반쯤 맞다"는 뜻은 아니다.
- 문서 전용어가 462개라 짧은 질문에서 우연히 걸릴 수 있다. 지금 평가에서는
  문제되지 않았으나 질문이 길어지면 오탐이 늘 수 있다.

## 섞을 때 쓸 만하다고 보는 부분

- **데이터에서 어휘를 수집하는 방식** — 다른 변형이 키워드 목록을 쓰더라도
  `lexicon.py`만 가져다 붙일 수 있다. 개체 이름·문서 전용어는 어떤 방식에도 도움이 된다.
- **순위 표현의 집계 대상 판별** — 규칙 방식이든 임베딩 방식이든 이 구분은 필요하다.
- **`reasons`·혼동행렬** — 임베딩 방식은 근거를 못 내므로, 규칙 신호를 근거 설명으로
  덧붙이는 조합이 가능하다.
